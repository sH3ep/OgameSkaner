# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

WPF desktop helper for the OgameX private OGame server (galaxy scanner, player search with spy actions, builder, raids, asteroid mining, expeditions, attack protection with fleet escape). Only OgameX is supported; support for other servers was removed deliberately.

## Commands

```powershell
dotnet build                                   # whole solution (OgameSkaner.sln)
dotnet test                                    # xUnit, tests/OgameSkaner.Core.Tests
dotnet test --filter "FullyQualifiedName~GalaxyPageParserTests"   # one class
dotnet test --filter "DisplayName~Parse_ignores_expedition"       # one test
dotnet run --project src/OgameSkaner.App
```

- `OgameSkaner.Core` has `TreatWarningsAsErrors`, so any new warning there breaks the build.
- The app targets `net8.0-windows` with `RollForward=Major`, because this machine has only the 9.x/10.x WindowsDesktop runtimes.
- There is no linter configured.
- Tests cover only `OgameSkaner.Core`; App code (view models, converters, XAML) has no tests, so check it with a build.
- While the app is running it locks `src/OgameSkaner.App/bin`, and `dotnet build` fails with MSB3021. To check that it compiles, build to another folder: `dotnet build src/OgameSkaner.App -o <temp dir>`.

## Architecture

Two projects plus tests. `Directory.Build.props` enables nullable and implicit usings everywhere.

- **`src/OgameSkaner.Core`** (`net8.0`, must stay free of WPF/Windows APIs):
  - **OgameX client:** `IOgamexClient`, one instance per universe, created by `OgamexClientFactory`.
    - Each client gets its own `CookieContainer` and a handler chain: `LoggingHandler → ThrottlingHandler → BrowserHeadersHandler → SocketsHttpHandler`.
    - `ThrottlingHandler` serializes **all** requests with a jittered minimum gap. Don't add per-request delays elsewhere.
    - The client tracks the game's current planet (`CurrentPlanet`, from every page that shows it). Calls that act on the current planet take their planet and switch first when it differs, under `_planetSwitch`: `EnqueueBuildingAsync` (the server refuses an upgrade for another planet), `GetFleetBriefingAsync(mission, origin)`, `SendFleetAsync(mission, origin)` and the unit orders.
  - **Action queue (`Services/Scheduling`):** every module acts in the game only through the universe's `IActionQueue` (`IActionQueues.For(client)`, one per client).
    - A module hands over a **group** of actions (`RunAsync(owner, description, work, priority)`), e.g. read a planet and queue its buildings, spy on N targets, one attack wave, the due expeditions, 5 systems of the asteroid scan, one system of the galaxy scan. It awaits the group's result, so the runners keep their loops.
    - `ActionQueue` runs one group at a time: player groups (`ActionPriority.User`, the pages' buttons) first, then the modules in turn (round robin by owner, FIFO within one), with a random pause when the turn passes to another owner (`Ogamex:ActionGapMin`/`ActionGapMax`, default 2–6 s; one owner's consecutive groups run back to back). A cancelled waiting group never runs; a failing group fails only its caller.
    - **No waits or CPU work inside a group** (they hold up every module): the Builder plans with the optimizer between its "Build on" groups and reads the planet again afterwards. A group that queues more work (a button's action whose waves are groups too) runs it inline.
    - **Switching back:** when the queue gets busy it reads the game's current planet (`HomePlanet`, the player's), and after `Ogamex:ReturnHomeAfter` (10 s, 0 = never) without a group it selects it again. The runners don't switch back themselves, and "the current planet" of a module means `HomePlanet` (Raids' home origin, the Players page's spy, the Utilities escape).
    - Exceptions: `AttackMonitor`'s checks (event list) aren't queued, and escapes use `RunUrgentAsync`, which runs at once next to a running group (its requests name their planet, so the group's next planet-bound request switches back by itself).
    - The App's `ActionQueueMonitor` shows the selected universe's queue on the **Queue** page and in the sidebar.
    - **History:** every finished group (done, failed, cancelled, urgent ones too) goes to `IActionHistoryStore` (`SqliteActionHistoryStore`, table `action_history`, schema step 5: owner, description, priority and state as names, queued/started/finished ticks, `wait_ms`, `run_ms`, error), kept 30 days (`KeptFor`; older rows are deleted on the first write of a run, then daily) for analysing the pacing. A failing write is logged and never stops the queue.
  - **Auth:** browser cookies (`gameAuthToken`, `SessionId`) are read from `ISessionStore` before every request. There is no login endpoint.
  - **JSON bodies:** camelCase (`JsonSerializerDefaults.Web`). This matches what the old RestSharp code sent.
  - **Parsers:** `Ogamex/Parsing/*` are pure static functions.
    - `GalaxyPageParser` is line-based on fixed markup markers (row start, `planet-index`, player-name span, `col-moon` + next-line length), ported from the original app. The player's line also gives the status classes (`isInactive7`, `isVacation`, …), the rank (the tooltip's `/statistics?rel=` link) and, on the line before it, the player id.
    - When content isn't a galaxy or fleet page (e.g. a login redirect), the parsers throw `SessionExpiredException`.
  - **Storage:** everything lives in `%AppData%\OgameSkaner` (`IAppPaths`).
    - `profiles.json`: universes plus the selected one.
    - `sessions.json`: values protected through `ISecretProtector`, which the App implements with DPAPI.
    - **Data vs. config:** game data (planets, scanned systems, history, spy reports, fleets sent) lives in SQLite. Settings and caches stay JSON.
    - `universes/<name>/data.db` (SQLite, `Storage/Sqlite`, package `Microsoft.Data.Sqlite`):
      - `UniverseDatabases` opens it. The first open in a run creates or upgrades the tables (`Schema`, `PRAGMA user_version`; add a step for a change and never edit an applied one) and imports the former JSON data once (see below). It also makes the daily backup.
      - Times are stored as UTC ticks (`Sql.Ticks`) and read back as local time.
      - `SqlitePlanetRepository` loads the whole `PlanetDatabase` into memory. A save writes only the systems replaced since the last one (`TakeChangedSystems`).
      - **History** is written on save. `slot_history` gets a row when a slot differs from before (new planet, other owner, moon, now free); `player_history` gets one when a player's name, status or rank changed. Players are keyed by id (`id:<id>`), or by name for scans without ids. The Players page shows both for the selected planet (`HistoryText`).
      - `SqliteRaidStore` keeps **all** spy reports (a re-read without details keeps the stored ships and defenses) and all fleets sent. Its settings stay in `raid-settings.json`.
      - `SqliteAsteroidStore` (schema step 3) keeps the asteroids seen, the miners sent and the mining reports. Its settings stay in `asteroid-settings.json`.
      - `SqliteActionHistoryStore` (schema step 5) keeps the action queue's finished groups for 30 days (see Action queue).
    - **Backups** go to `backups/<name>/`:
      - `data-<time>-daily.db` at most once a day (the first open of a run), plus copies before a schema upgrade and after the import. The newest 7 are kept.
      - `json-<time>/` holds the JSON data files as they were before the import. After the import they're renamed to `*.migrated`.
    - The JSON stores of that data (`JsonPlanetRepository`, the reports and fleets in `JsonRaidStore`) are only read for the import. `planets.json` versions: 2 added player status, id and rank; 3 added the scanned systems.
    - `universes/<name>/scan-settings.json`: the Scanner page's pacing (`IScanSettingsStore`, `ScanSettings`): a random delay between two systems' requests (measured from the previous request, so `Ogamex:MinRequestInterval` stays the floor) and a longer pause after every N systems. Only `GalaxyScanService` uses it.
    - `universes/<name>/build-settings.json`: the Builder page's strategy and last run options (`IBuildSettingsStore`), including the planets the user unticked (`ExcludedPlanetIds`, so new colonies are included by default).
    - `optimizer-results.json` (shared): the Optimizer page's last setup and the best order per setup.
    - `schemas.json` (shared by all universes): the schema library; `universes/<name>/schema-assignments.json`: which schema each planet follows and whether it runs.
    - `universes/<name>/own-planets.json`: the player's own planets (id, name, coordinates) and moons (`Moons`, only the Expeditions page uses them), refreshed by `OwnPlanetService` (Refresh buttons on the Builder, Schemas and Shipyard pages, and at the start of every build run, raid cycle, colonization and ship order).
    - `universes/<name>/raid-settings.json`: the Raids page's settings (`IRaidStore`; its reports and fleets are in `data.db`).
    - `universes/<name>/asteroid-settings.json`: the Asteroids page's settings (`IAsteroidStore`; its asteroids, missions and reports are in `data.db`).
    - `universes/<name>/defense-settings.json`: the Defense page's options; `alert-settings.json` (shared): the enabled alert channels and their options (`IDefenseSettingsStore`).
    - `universes/<name>/expedition-settings.json`: the Expeditions page's ship types, origins with their counts and options (`IExpeditionSettingsStore`).
  - **Build automation:** `Domain/Buildings` (catalog with server ids, cost factors and energy formulas; strategy), `Services/Building/BuildPlanner` (pure: cheapest affordable next upgrade by weighted value metal 1 / crystal 1.5 / deuterium 3, skipping locked buildings; solar only when energy runs out; storage targets like any other) and `SimulatedBuildRunner`, which runs the Builder modes (`BuilderMode` in `SimulatedBuildOptions`/`BuildSettings.Mode`): **Simulated** (see "Builder's Simulated mode" below; afterwards the buildings the simulation doesn't know go by price), **ByPrice** (no simulation: `BuildPlanner.Plan` for all ticked rules, cheapest first) and **ByLevel** (no simulation: `BuildOrder.ByLevel`, the next level furthest below its target first, cheapest among equals, so Relative rules keep their offsets to each other and rise one level at a time). All queue through `BuildInOrderAsync`: as many levels as the resources cover on top of the waiting items (`SimulatedPlanner.AffordablePrefix`), not one per cycle. The old Single/Auto modes were removed as inferior.
    - A run works on the planets ticked on the Builder page (`BuildRequest.Planets`), one queue group per 5 planets ("Build on A, B, …"; the planets that need a new plan get one more group after the search).
    - Endpoints and server quirks are documented in `docs/ogamex-build-api.md`. State comes from `/building/resource` and `/building/facility` (`BuildingPageParser`), switching planet with `?planet=<guid>` (global server-side state, the browser follows); upgrades are `POST /building/increasebuilding` with PascalCase `{BuildingType, __PlanetId}`.
    - Costs: the next level's cost is read from the page (OgameX mine costs don't follow a formula); the catalog factor only extrapolates further levels.
    - Storages: a ticked storage rule's target (default Absolute 0 = none) is an `OptimizerSetup` target like the factories (`MetalStorageTarget` etc.), so unticking everything else builds only storages. `StorageFillPercent` (default 70, 0 = off) is applied inside the simulation (see below), only to the ticked storages (`BuildStrategy.FillsStorage` → `OptimizerSetup.FillStorages`); an unticked storage is still built when a cost doesn't fit in it. `BuildPlanner`'s own page-based storage rule is off when the runner uses it for the other buildings.
    - Only planets are automated (moons get their own automation later): the parser skips sidebar links marked as moons and the client refuses a page without a metal mine. Free fields (`remainingFieldsQueueIncluded`, resources page only) cap the plan; vacation mode (`window.isVacation`) stops the run for that planet.
    - Energy: the solar plant is driven by energy, not price. The starting point is the game's balance (`resources.energy − resources.energyConsumption`, bonuses from research/officers/class included); only the difference of planned levels comes from base formulas (`EnergyFormulas.Projected`). The per-building energy numbers on the page are base formulas shifted by one level, so don't use them.
    - The server checks each new queue item against the planet's actual resources and takes them only when the item starts. It answers `IsSuccess: true` but **silently ignores** an unaffordable item, so the service verifies every queued item on the next state read. The queue holds 15 (running + 14 waiting).
  - **Build schemas:** `Domain/Schemas` (`BuildSchema` = ordered absolute steps like "Crystal Mine 2" + `SchemaRules`), `Services/Schemas/SchemaPlanner` (pure: next action for a planet – solar plant then solar satellites when energy runs out, storage at fill %, Robotics/Nanite when the saved construction time of the next 15 steps exceeds their build time + cost as production time, then the next step in strict order) and `SchemaRunner` (continuous virtual queue: each cycle pushes what the planner allows, one queue group per planet, then waits the check interval).
    - The game **drops a queued item whose resources are missing when its turn comes**, so the schema planner only pushes an item when resources cover it plus all waiting queue items, and keeps the game's queue shallow (`MaxServerQueueDepth`, default 3).
    - Shared planning helpers (page-anchored costs/durations, storage rule) live in `Services/Building/PlanningRules.cs`. The App's `AutomationActivity` lets only one of Builder/Schemas run at a time.
  - **Build order optimizer:** `Domain/Optimizer/GameModel` (OgameX formulas measured on genesis: costs, construction times with Robotics `(1+R)·1.05^R` and Nanite `1.8^N`, production, energy, storage capacity, satellites; see the docs' "Formulas for the optimizer" and "Account bonuses"). Its parameters are `AccountBonuses` (research/officers/academy/premium/ranking add up, class bonus multiplies; construction/ship speeds divide time), read from `/resource`, `/officer` and `/academy` by `GetAccountBonusesAsync` before every run, and `PlanetConditions` (slot bonus, temperature). `AccountBonuses.Calibration` holds the bonuses the measurements were taken with, which the model divides out; `Services/Optimizer/BuildSimulator` (event simulation of one order on a fresh planet: one building at a time, satellites in parallel, resources taken at the start, production capped by storage) and `BuildOrderOptimizer` (N independent runs on below-normal-priority threads, 90% of the cores by default: randomized greedy start + simulated annealing). Speed: the simulator state is one value type (`SimState`), saved every 8 genes in an `EvaluationTrace`; a candidate resumes from the last checkpoint before the first gene its mutation changed (moved back further when an earlier satellite gene looked ahead past it), bit-for-bit equal to a full run (`Resuming_from_a_checkpoint_gives_exactly_the_full_result`). Satellites finished while energy already covers the mines are counted in O(1). Core is compiled with `Optimize=true` even in Debug (unoptimized code was ~6x slower). Results: `optimizer-results.json` in the app folder, best order per `OptimizerSetup.Key` (includes `GameModel.Version`; bump it when a formula changes). The Optimizer page can save an order as a schema.
  - **Builder's Simulated mode:** `Services/Building/SimulatedBuildRunner` (continuous, like the schema runner) plans each planet with the optimizer from its real state (`OptimizerSetup.Start` = `PlanetStart`: levels, resources, satellites, queue with the running item's remaining seconds; the simulator finishes the queue first and counts time from now) to the strategy's targets, with `CoverEnergy` (done only when energy covers the mines; satellites for an energy shortage in the real queue are ordered at time 0, the plan's first step), `StorageFillPercent` (the simulator builds a storage level before an item that would leave its resource at ≥ that share of capacity, so the storage is in the plan and the game queue at the right point; not applied to the real queue it finishes first; skipped when the resource would refill to that share of the new capacity while the storage is built, which used to raise storages one after another to the highest level), `MineBalancePercent` (default 30, 0 = off: while the lowest mine below its target has a next level costing less than that share of the dearest next mine level, every mine gene builds it; `BuildSimulator.MineFor`, so a mine gene can build another mine, but each still builds one level), `EarlyRoboticsLevel`/`EarlyRoboticsMineLevel` (default 6 / 10: the simulator inserts Robotics levels before a mine passes that level; the search alone builds Robotics late), `KeepMinesPowered` (always on for the Builder: before a mine level short of energy the simulator inserts Solar Plant levels up to the max, then satellites with the Robotics 3 / Shipyard 3 they need, at least `MinSatelliteOrder` (30) per order; without it the fastest order leaves mines unpowered until the end because construction time, not production, limits genesis plans) and per-planet corrections (extra energy, production ratios vs. the page). `SimulatedPlanner` (pure) builds the setup and picks what to push (resources cover it plus all waiting items). It re-plans whenever the planet changed, seeds the search with the previous plan, and sleeps until the next item is due (10 s–5 min). Temperature comes from `/home` (`OverviewPageParser`).
  - **Raids (inactive farmer):** endpoints in `docs/ogamex-raid-api.md`.
    - `Services/Raiding/RaidPlanner` (pure): candidates are raidable inactives from the galaxy database (`PlayerStatus.IsRaidable`), best rank first, limited by `RaidSettings.MaxRankingDefensePoints` (null = no limit; with a limit, players not in the defense ranking are skipped; the grid's `RaidTargetFilter` is a separate view filter); each gets a `RaidTargetState` from its newest report and the fleets sent (spy when there's no report, it's older than `ReportMaxAge` or from before our last attack, except that a report with loot below `MinLoot` isn't re-spied for `LowLootRespyHours` (default 5, unless we attacked since); ready when the report's defense and fleet points are within the limits and the loot ≥ `MinLoot`).
    - Reports: `EspionageReportParser` reads the list (`/messages/messagedata?MessageCategoryType=FLEET_ESPIONAGE`) and the detail page (`/messages/spyreportdetail`). A section's header shows **points** (`Defenses (2.000)` = 1,000 missile launchers), which is what the limits use; a section the probes didn't see has no number (`Unseen`). Labels follow the language cookie, so parsing goes by structure.
    - Defense ranking: `StatisticsPageParser` reads `/statistics/statisticsdata?Category=PLAYER&SubCategory=DEFENSE&Page=n` (100 players per page; the player id is the galaxy's GUID). `RaidRunner.ReadDefenseRankingAsync` reads every page into the `rankings` table (schema step 2); a run re-reads it when older than `RankingMaxAge` (6 h). `RaidTarget.RankingDefensePoints` shows it in the grid: 0 = no defenses, safe to attack. The planner uses it only for a report that hides sections: ranking 0 counts as no defenses and, since inactives keep no fleet, hidden ships as no fleet too. A target whose report still hides something although our spy sent at least `ProbeCount` probes stays `Unseen` and isn't spied on again (that used to loop: re-spy every `ReportMaxAge`, never attack).
    - `RaidRunner`: each cycle reads slots (`Fleets: x/y`) and new reports, attacks ready targets (most loot first) and spies on the next ones (best rank first); with `NearestTargetsFirst` (default on) both go nearest first (`RaidPlanner.NearestFirst`, stable, so ties keep that order; ignored with `UseNearestPlanet`, which takes targets from the whole universe: spies best ranked first, attacks most loot first, each fleet from the nearest planet of `OriginPlanetIds` (ticked on the page, new planets unticked, none = nothing sent) that has the cargo ships or probes), attacks within `FleetSlotUsePercent` of the slots, spies only while the slots in use (with the attacks just sent) are below that share, then in every slot but one, so a batch may go past it (`RaidPlanner.SpySlotBudget(slots, settings, sent)`; "Spy selected" ignores the share), then sleeps until a report is due or a fleet returns. Cargo = loot × (1 + margin), filled by `RaidPlanner.CargoFleet` from `RaidSettings.CargoShipTypes` in priority order (the first type as far as the planet has it, then the next; empty = the older single `CargoShipType`), each type's capacity from the fleet page's tooltip (technology included). A mixed attack is stored as one `RaidRecord` with the types joined by `+` and the total ship count. One report can get up to `MaxAttacksPerTarget` (default 4) attacks: first one per target, then further waves while `RaidPlanner.WaveLoot` (Loot % of what the earlier waves left) is ≥ `MinLoot`. A wave must land `RaidPlanner.MinWaveGap` after the previous one on that planet: a shortfall up to 30 s is waited out, a longer one lowers the speed in 10% steps (re-asking the briefing), else the wave isn't sent. The briefing flies from the server's current planet, so `AttackAsync` selects the origin's fleet page first. Every send is checked first with the read-only briefing `/fleet/fleetpage3data` (flight time, possible missions, the player's status).
    - `/fleet/submitfleet` has **no origin**: fleets leave from the server-side current planet. `OgamexClient.SendFleetAsync(mission, origin)` therefore switches with `fleet?planet=` and submits under `_planetSwitch`, a lock every planet-switching request takes, so the Builder can run at the same time. Mission ids: 5 = Deploy (the fleet escape), 6 = Spy, 8 = Attack.
  - **Asteroid mining:** endpoints and game rules are in `docs/ogamex-asteroid-api.md`.
    - **Finding:** `/galaxy/Partial_AsteroidLocation` lists system ranges at position 17, one row per asteroid; rows overlap and repeat. `AsteroidParser` reads it and the galaxy page's `a.btn-asteroid` (`data-asteroid-disappear` = seconds left). `GalaxyPageParser` still stops at position 16; `GetGalaxySystemAsync` returns both.
    - **`AsteroidPlanner.Uncovered`** matches each hint row to its own known asteroid (by the row's end). The runner scans the rows left over, system by system, until each has one. Scanned systems also go into the galaxy database.
    - **Reports:** `FLEET_ASTEROID_MINING_REPORT` messages in the `FLEET_OTHER` tab. Each resource line reads gained / held, and the held amounts added up are `AsteroidReport.Available`; other results are text only (`AsteroidParser.ParseReports`).
    - **`AsteroidEstimator`** (pure) works from the daily decline: gains drop 2% per successful mining (any result but nothing), down to 40%, and reset at 00:00 UTC on the arrival day. Within a day it takes the day's last 4 reports with resources (fewer when there are fewer), works each back to full gains and scales the biggest; on a new day it uses the first report of the latest earlier day. Without such a report the runner sends `MinersWithoutEstimate` (1,000,000).
    - **Sending:** miners = estimate × (1 + margin) / cargo per miner (fleet page tooltip), capped by `MaxMiners` (null = no limit, also caps `MinersWithoutEstimate`); not sent at all when their cargo holds less than `MinCoveragePercent` (default 70, 0 = off) of the estimate (`AsteroidPlanner.CoversEnough`; no estimate = no check). "Fleet recalled" (`AsteroidRunner.MarkRecalled`) sets the asteroid's last mission's `recalled_at` (schema step 4) when the player turned the miners back in the game; a recalled mission doesn't count, so the asteroid is open and gets miners again. They leave from the nearest planet with enough (otherwise the nearest with any) when the briefing's flight arrives `ArrivalSafetySeconds` before the asteroid is gone. Mission id 12, target z = 17, planet type 1.
    - **`AsteroidRunner`** is continuous, like `RaidRunner`: each cycle reads reports, sends miners to the known open asteroids (gone soonest first, nearest first among equals), then scans the hinted systems nearest to a planet with miners first (`AsteroidPlanner.ScanOrder`) and sends miners to the new asteroids at the end of each scan group, gone soonest first, stopping the scan once no miners or fleet slots are left (queue groups: reports + known asteroids, then the scan in groups of 5 systems); then it sleeps until a report is due, a fleet returns or the check interval passes.
  - **Attack protection (Defense page):** endpoints in `docs/ogamex-defense-api.md`.
    - **Detection:** `FleetMovementParser` reads the event list (`/home/fleetmovementlist`): mission and relation from the row classes (`row-mission-type-ATTACK`, `row-hostile-mission`, `row-fleet-return`), time from `data-remaining-seconds`. The hostile row markup is inferred from the game's CSS (no attack was seen yet), so check the fixture against the first real one.
    - `Services/Defense/DefensePlanner` (pure): which attacks are due (`EscapeSecondsBeforeArrival` before impact, at once when seen later; spies and missiles are alert-only), the wait (check interval, shorter when an escape falls due), the target (a target named unlike the planet at its coordinates is the moon: alerted, not escaped, since moons aren't in the planet list), the destinations (moon, then the 3 nearest planets not under attack) and the cargo (deuterium minus fuel, crystal, metal up to the capacity; satellites and crawlers stay).
    - `AttackMonitor` (continuous): each check alerts once per new hostile fleet id, escapes the due attacks with Deploy at `EscapeSpeedPercent` (default 10%), trying each destination's briefing (no moon = no Deploy or a refusal), without waiting for the action queue (`RunUrgentAsync`). A failed escape, 3 failed checks in a row and an expired session (which stops it) are alerts too. Fleets aren't recalled after the attack.
    - **Alerts:** `Domain/Alerts` (`Alert`, `IAlertChannel`, `AlertSettings`) and `Services/Alerts/AlertDispatcher`, which sends to every enabled channel at once and logs a failing one without stopping the others. The monitor doesn't await alerts, so a slow channel can't delay an escape. The App registers `WindowsAlertChannel` (tray icon balloon = Windows notification, the reason the App has `UseWindowsForms` with its global usings removed) and `SoundAlertChannel` (plays through `AlarmPlayer`: `MediaPlayer` on the UI dispatcher, the chosen .wav/.mp3, default `Resources/Sounds/alarmSignal.mp3` copied to the output, the Windows sound when it can't play; Critical repeats `SoundRepeat` times, Warning (spy probes) plays at most 3 s, Info is silent; the sidebar's "Stop alarm" (`AlarmPlayer.StopCommand`) silences what plays, the next alert plays again). **A new channel** (e-mail, SMS) is one `IAlertChannel` class (in Core when it needs no Windows API) plus one `AddSingleton<IAlertChannel, …>` line; it shows up as a checkbox on the Defense page. Its options go into `AlertSettings`.
    - The sidebar shows its state (`DefenseViewModel.ProtectionStatus`: off / watching / hostile fleets) instead of a list of running modules; the green dots next to the page names show those.
    - The Defense page's "Start with the app" starts it from `App.OnStartup` and on a universe change, without opening the page.
  - **Expeditions:** endpoints in `docs/ogamex-expedition-api.md`.
    - `ExpeditionSettings`: the ticked ship types (no amounts: all of them go), the origins (planets or moons, by id) with how many expeditions each keeps in the air, the duration, speed and fleet slots kept free.
    - `Services/Expeditions/ExpeditionPlanner` (pure): target `[g:s:16]` of the origin's system; in flight per origin = own `EXPEDITION` rows of the event list from its coordinates, once per fleet id (a planet and its moon share coordinates, so then the row's name decides); budget = min(free expedition slots, free fleet slots − kept); each expedition takes ⌈ships home ÷ expeditions the origin still sends⌉ of every ticked type (satellites and crawlers never fly, `UnitCatalog.CanFly`); the duration nearest to the setting among the briefing's `ExpeditionKeepValues`.
    - `ExpeditionRunner` (continuous, like `AsteroidRunner`): each cycle refreshes planets and moons, reads the event list, sends the missing expeditions in the settings' order (fleet page of the origin, briefing must offer mission 1, then `submitfleet` with `HoldTimeOnMinutes`) in one queue group, and sleeps until an expedition arrives or returns (+30 s) or the interval passes. It also counts what it sent until the computed return, in case the event list hides holding expeditions. A refusal moves on to the next origin.
    - Moons: `BuildingPageParser.ParseMoons` (inferred markup, the account had none) fills `OwnPlanetsSnapshot.Moons`/`OwnPlanetList.Moons`; the other pages still use `Planets` only.
    - "Start with the app" works like the Defense page's.
  - **Shipyard page:** `Services/ShipyardService` orders the same ships or defenses (`UnitCatalog`, by `UnitKind`) on every ticked planet, one request each; a refused planet is reported and the rest still get theirs; the whole order is one player group of the queue. `IOgamexClient.BuildShipsAsync`/`BuildDefensesAsync` load the planet's `hangar`/`defense` page first and post under `_planetSwitch` (see `docs/ogamex-build-api.md`).
  - **`PlanetDatabase`:** a thread-safe in-memory store keyed by solar system. `IPlanetRepository.GetAsync` (`SqlitePlanetRepository`) returns the **same instance** per universe, so the scanner and the players page share data.
  - **Colonization:** `Services/ColonizationSearch` (pure) lists free slots (positions 1–15) in a galaxy/system/slot range. A slot counts as free when its system is in `ScannedSystems` and no planet was seen there. Free slots aren't stored. `ColonizationService` sends one Colony Ship (mission 2) from the nearest own planet that has one (fleet pages are read nearest first). It checks the briefing for `Colonize` first; the whole send is one player group of the queue.
  - **`Storage/Legacy/LegacyImporter`:** migrates the old .NET Framework app's `GamesConfiguration.xml` and `DatabaseOgameX{uni}.xml`. Its tokens use the old hard-coded AES key in `LegacyTokenDecryptor`, which is only for migration.
  - **DI:** services are registered in `ServiceCollectionExtensions.AddOgameSkanerCore`.
- **`src/OgameSkaner.App`** (WPF, `Microsoft.Extensions.Hosting`, CommunityToolkit.Mvvm, Serilog):
  - `App.xaml.cs` builds the host and is the composition root. There is no `StartupUri`.
  - Config comes from `appsettings.json`, with an optional per-user override at `%AppData%\OgameSkaner\appsettings.json`. Set `Ogamex:DumpResponsesDirectory` there to capture raw responses as test fixtures.
  - **Pages are view-model-first:**
    - `services.AddPage<TViewModel, TView>("Title")` registers a singleton `PageViewModel` and a `PageDescriptor`.
    - `PageRegistration.RegisterTemplates` generates the implicit DataTemplates.
    - `MainViewModel.CurrentPage` drives a `ContentControl`.
    - Adding a page means a view model, a `UserControl` and one `AddPage` line.
  - **`IUniverseContext`** holds the selected `UniverseProfile` and its `IOgamexClient`. Pages subscribe to `CurrentChanged`; the scanner cancels a running scan there.
  - **View models never show windows or message boxes directly.** They use `IDialogService`.
  - **Cross-page notifications** go through `IMessenger`, for example `SessionSavedMessage` triggers a session re-check.
  - **Remembered layout:** `infra:Layout.Key="Page.Part"` (`Infrastructure/Layout.cs`) on a window, a grid with a `GridSplitter` or a `DataGrid` keeps its sizes (window bounds, column/row lengths, column widths and order) in `%AppData%\OgameSkaner\layout.json` (`LayoutStore`): restored on Loaded, saved on Unloaded and when the main window closes; ignored when the column/row count changed. Give every new splitter grid and data grid a key.

## Conventions and gotchas

- **New endpoints:**
  - Add a method to `IOgamexClient`/`OgamexClient` and DTOs in `Ogamex/Dto.cs`.
  - Put HTML parsing in `Ogamex/Parsing` with a fixture under `tests/.../Fixtures`, which is copied to the output directory.
  - Test services against `FakeOgamexClient` and `FakePlanetRepository` in `tests/.../Fakes`.
- **Universe names** become a sub-domain (`https://{name}.ogamex.net`). Always validate them with `UniverseProfile.IsValidName`.
- **Implicit usings:** WPF projects don't include `System.IO`, so add `using System.IO;` in App code when needed.
- **Number fields:** bind editable numbers with `Converter={StaticResource GroupedNumber}` (thousands separators, accepts them when typed, empty = null for nullable types) and the default `LostFocus` trigger. `StringFormat=N0` with `UpdateSourceTrigger=PropertyChanged` reformats while typing, moves the caret and can't parse "10,000" back.
- **Planet-bound actions:** some requests act on the server's current planet, not the one in the body (`/fleet/submitfleet` has no origin at all). Give the client method the planet, switch with the planet's page when `CurrentPlanet` differs and send under `_planetSwitch`, as `EnqueueBuildingAsync`, `GetFleetBriefingAsync` and `SendFleetAsync` do. Never rely on "the last page read selected it".
- **New automation:** put every request to the game into `IActionQueue` groups (one group = what a player would do in one go on one page or planet); keep planning and waiting outside them, and don't switch back at the end.
- **Continuous runners** (Raids, Asteroids, Expeditions, Defense, Builder, Schemas) wait between cycles with `WakeUp.DelayAsync` (`Services/Scheduling/WakeUp.cs`, reset when the run starts) and expose `CheckNow()`, which the pages' "Check now" button calls (enabled while running); a press during a cycle ends the next wait at once. A new continuous runner does the same.
- **Legacy data:** the untracked `OgameSkaner/bin/Debug` folder (leftover of the old project) holds the user's real legacy data and session tokens. Don't delete it. Treat it as read-only and sensitive.
- **Never commit:** local data files (`GamesConfiguration.xml`, `Database*.xml`, `profiles.json`, `sessions.json`) are gitignored.
